    $ failora detect --list
    
      
    What Failora detects
    
      
    Each category is marked as available today or planned. Examples show the kind of finding you would see, not live results.
    

      
    
        
    
          
    AVAILABLE
    
          
    AI retry, fallback and recovery
    Checks whether retries and fallbacks actually run when an AI call fails.
    
          
    example: HTTP 429 received, no retry and no fallback.
    
        
    
        
    
          
    AVAILABLE
    
          
    API failures and performance
    Runs timeout, 429, 500 and malformed scenarios against an endpoint.
    
          
    example: POST /respond: 6% HTTP 500 in the sample run.
    
        
    
        
    
          
    AVAILABLE
    
          
    Regression tests from failures
    Turns a failing scenario into a repeatable test.
    
          
    example: timeout scenario saved as a test for every commit.
    
        
    
        
    
          
    PLANNED
    
          
    Website health and availability
    Checks that a public URL responds, and how fast it does.
    
          
    example: homepage returned 503 on 2 of 20 checks.
    
        
    
        
    
          
    PLANNED
    
          
    Security and configuration gaps
    Flags missing headers and settings that weaken a deployment.
    
          
    example: Content-Security-Policy header is not set.
    
        
    
        
    
          
    PLANNED
    
          
    Repository reliability issues
    Finds code paths that can hang or fail without handling.
    
          
    example: src/client.ts:42 fetch() has no timeout.

    Run it locally in a few commands
    
      
    These are the commands from the project README. Nothing here is simulated.
    

      
    
        $ git clone https://github.com/madhavikodale/Failora.git
        $ cd Failora
        $ npm install
        $ cp .env.example .env
        $ npm run mock-ai # mock AI service, bound to 127.0.0.1
        $ npm run start --workspace=packages/api # API on port 4200
        $ npm run test
        $ npm run typecheck
      
    

      
    API endpoints
    
      
    
        
    
          
    MethodEndpointDescription
    
          
            
    GET/healthHealth check
    
            
    POST/targetsCreate a test target
    
            
    GET/targetsList all targets
    
            
    GET/targets/:idGet target by ID
    
            
    DELETE/targets/:idDelete target
    
            
    POST/runsExecute a scenario (async, returns 202)
    
            
    GET/runs?target_id=List runs, filtered by target
    
            
    GET/runs/:idGet run result
    
              
        
    
      
    

      
    Mock AI failure modes
    
      
    
        
    
          
    RequestWhat it does
    
          
            
    ANY /respond?mode=okNormal 200 response
    
            
    ANY /respond?mode=slow&delay=5000Delays, then responds. Use for timeout tests
    
            
    ANY /respond?mode=429Returns HTTP 429 with Retry-After
    
            
    ANY /respond?mode=500Returns HTTP 500
    
            
    ANY /respond?mode=malformedReturns invalid JSON
    
              
        
    
      
    

      
    Create a target and run a scenario
    
      
    
        $ curl -X POST http://127.0.0.1:4200/targets -H "Content-Type: application/json" \
            -d '{"name":"my-api","url":"http://127.0.0.1:4100/respond"}'
        $ curl -X POST http://127.0.0.1:4200/runs -H "Content-Type: application/json" \
            -d '{"target_id":"TARGET_ID","mode":"timeout","timeout_ms":1000,"max_retries":2}'
        $ curl http://127.0.0.1:4200/runs/RUN_ID
      
    
      
    Replace TARGET_ID and RUN_ID with the values returned by the API.

    $ cat why-failora.txt
    
        
    
          
    Detection with recovery verification. Finding a failure is half the job; Failora checks that retries and fallbacks recover.
    
          
    Evidence-based findings. Each issue links to the request, file or line behind it.
    
          
    Repeatable regression tests. A failure becomes a test that runs on every change.
    
          
    Website and code in one workflow. Planned: check what users reach and what your code does, in one report.
    
        
    
      
    
      
    
        
    $ failora privacy
    
        
    
          
    This demo runs a simulated scan in your browser. The URL you type is not sent to any server.
    
          
    Scanning you run: only URLs you own or have permission to test.
    
          
    Failure injection runs against a localhost-only mock service.
    
          
    Repositories: access rules will be documented before launch. Read access is limited to repositories you choose.

    $ failora help --faq
    
      
    
        
    
          What does a URL scan check?
          
    The planned URL scan will check whether the page responds, how long it takes, and common header and configuration settings. Only scan URLs you own or have permission to test.
    
        
    
        
    
          How does a private repository connect?
          
    Repository analysis is planned. The connection flow and access rules will be documented before launch.
    
        
    
        
    
          How is recovery verification done?
          
    Failora injects controlled failures such as timeouts, HTTP 429, HTTP 500 and malformed responses into your target. It then checks whether retries and fallbacks run, and records success rate and latency.
